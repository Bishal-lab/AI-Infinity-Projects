# Build guide

This is built as **two kinds of Make scenario**, not one giant scenario:

1. **Watcher scenarios** (one per search feed) — watch a feed, ask the LLM
   whether each new posting is relevant, and store the relevant ones.
2. **One digest sender scenario** — runs on a schedule, collects everything
   the watchers stored since the last run, and sends a single sorted Telegram
   message.

Why split it this way, instead of one scenario looping over every feed:
- Make's **"Watch RSS feed items"** trigger already does polling *and*
  new-item-only deduplication natively per feed — reusing it means this
  project doesn't need to hand-roll XML parsing or a dedupe cache, both of
  which would otherwise need a scripting module Make doesn't guarantee on
  every plan.
- Fanning results into a shared **Data Store** and sending from one place
  means you get one combined, location-sorted digest instead of a separate
  Telegram ping per feed per poll.
- Adding a new search later is "clone a watcher scenario, change the feed
  URL" — no shared logic to touch.

There's no importable blueprint `.json` for this project (unlike this repo's
n8n project). Make blueprint exports embed internal numeric module/app
version IDs and connection references that are only generated by an actual
Make account building the scenario — they can't be hand-authored reliably the
way n8n's more portable node-type strings can, and a broken import in Make
tends to fail as an opaque "invalid blueprint" error rather than degrading
node-by-node like n8n does. The module-by-module steps below are the
authoritative build path.

## Shared setup (once)

### Data Store: `Job Alerts`

**Data stores → Add a data store** → name it `Job Alerts`. Add these fields:

| Field | Type |
|---|---|
| `title` | Text |
| `link` | Text |
| `sourceLabel` | Text |
| `locationTier` | Number |
| `locationText` | Text |
| `reason` | Text |
| `notified` | Boolean |
| `discoveredAt` | Date |

### Telegram bot

Same as any Make Telegram integration: message **@BotFather** →
`/newbot` → copy the token. Message your new bot once (any text, e.g.
`/start`) so it's allowed to message you back. Get your chat ID either from
**@userinfobot** or by opening
`https://api.telegram.org/bot<YOUR_TOKEN>/getUpdates` right after messaging
the bot and reading the numeric `chat.id`. Add a **Telegram Bot** connection
in Make using the token.

### OpenAI connection

**Connections → Add → OpenAI** → paste your API key from
[platform.openai.com](https://platform.openai.com).

### Google Alerts feeds

Follow [`../docs/search_queries.md`](../docs/search_queries.md) to create the
two Google Alerts (RSS delivery) and get their feed URLs before building the
first watcher scenario.

## Scenario type 1 — Watcher (build once, clone for each feed)

Create a new scenario, name it **"Job Watcher: Life Insurance VP"** (build
this one first; see [`feed_urls.md`](feed_urls.md) for the full list to clone
afterward).

**Module 1 — RSS → Watch RSS feed items**
- This is the scenario's trigger; add it first.
- **Feed URL**: the Google Alerts RSS URL for Alert 1 (Life Insurance VP).
- **Maximum number of returned items**: 20.
- Leave everything else default — this module's own dedup means it only
  emits items it hasn't emitted before.

**Module 2 — OpenAI (ChatGPT, Whisper, DALL·E) → Create a Chat Completion**
- **Model**: `gpt-4o-mini` (or `gpt-4o` if you want higher accuracy at higher
  cost).
- **Messages**: add a `system` message and paste the **System message** block
  from [`relevance_classifier_prompt.md`](relevance_classifier_prompt.md)
  verbatim. Add a `user` message using the template in that same file, with
  `[RSS trigger → title]` etc. replaced by clicking Module 1's `title`,
  `description`, and `link` output fields from the mapping panel, and
  `Source` hardcoded to `Google Alerts — Life Insurance VP` for this
  particular scenario.
- If your module version offers a **Response format** option, set it to
  **JSON object** — this makes the reply reliably parseable JSON. If not,
  the prompt's own "return ONLY this JSON" instruction is usually enough.

**Module 3 — JSON → Parse JSON**
- **JSON string**: Module 2's completion text output (the assistant's reply
  content field).
- **Data structure**: click **Add**, then **Generate** and paste the contents
  of [`classification_json_schema.json`](classification_json_schema.json) to
  auto-create the field list (`relevant`, `role_match`, `industry_match`,
  `location_tier`, `location_text`, `accepts_indian_profile`, `reason`).

**Filter** (on the connector between Module 3 and Module 4) — click the
connector, name it "Relevant only":
- Condition: Module 3's `relevant` field → **Boolean equal to** → `true`.

**Module 4 — Data Store → Add/Replace a Record**
- **Data store**: `Job Alerts`.
- **Key**: Module 1's `link` field (this makes re-adding the same job, if a
  different feed surfaces it too, overwrite rather than duplicate).
- Map fields: `title` ← Module 1 `title`, `link` ← Module 1 `link`,
  `sourceLabel` ← the hardcoded label for this scenario, `locationTier` ←
  Module 3 `location_tier`, `locationText` ← Module 3 `location_text`,
  `reason` ← Module 3 `reason`, `notified` ← `false`, `discoveredAt` ←
  `{{now}}`.

**Scheduling**: click the clock icon at the bottom of the scenario editor →
**Run at regular intervals** → every 6 hours (or your preference — Google
Alerts itself typically only batches about once a day, so polling much more
often than that mainly means picking up a new day's batch sooner, not
catching things Google hasn't indexed yet).

**Activate** the scenario (toggle top-right).

### Cloning for the rest of the feeds

Right-click the scenario in the scenarios list → **Clone**. In the clone:
1. Rename it per [`feed_urls.md`](feed_urls.md).
2. Open Module 1, replace the **Feed URL**.
3. Open Module 2, replace the hardcoded `Source` value in the user message.
4. Activate.

Everything else (the prompt, the Data Store, the dedupe-by-link key) is
already correct and doesn't need touching.

## Scenario type 2 — Digest sender (build once)

Create a new scenario named **"Job Alert Digest Sender"**.

**Module 1 — Data Store → Search Records**
- This is the scenario's first module — Data Store actions can start a
  scheduled scenario without a separate trigger app.
- **Data store**: `Job Alerts`.
- **Filter**: `notified` → **Boolean equal to** → `false`.

**Module 2 — Array Aggregator** (Flow Control / Tools)
- **Source Module**: Module 1 (Search Records).
- **Target structure type**: Text.
- **Row template** (one row per record found):
  ```
  {{if(locationTier=1;"🟢 Delhi NCR";if(locationTier=2;"🟡 India (other)";if(locationTier=3;"🔵 UAE";if(locationTier=4;"🟣 Australia";"⚪ Other"))))}}
  *{{title}}*
  📍 {{locationText}} | via {{sourceLabel}}
  _{{reason}}_
  🔗 {{link}}
  ```
- **Separator**: two newlines (`\n\n`).
- **Sort by**: `locationTier`, ascending.

**Filter** (on the connector after Module 2) — name it "Has new jobs":
- Condition: Module 2's aggregated text → **Exists** (skip the run entirely
  if there's nothing new — avoids "no new jobs today" pings).

**Module 3 — Telegram Bot → Send a Text Message**
- **Chat ID**: your chat ID from the shared setup above.
- **Text**: `🔔 *New role matches found*\n\n` followed by Module 2's
  aggregated text.
- **Parse mode**: Markdown.

**Module 4 — Iterator** (Flow Control)
- **Array**: Module 1's records array (the raw Search Records output, not
  the aggregated text — this loop is to mark every found record as notified).

**Module 5 — Data Store → Update a Record**
- **Data store**: `Job Alerts`.
- **Key**: the current iteration's record key (Make exposes each Data Store
  record's own key as a mappable field on the Iterator's output — click it
  from the mapping panel rather than typing it by hand, since the exact field
  name can vary slightly by Make version).
- Set `notified` → `true`.

**Scheduling**: every 6 hours, offset ~15–30 minutes after the watcher
scenarios so there's time for a watcher's OpenAI/Data Store steps to finish
before the digest sender reads the store.

**Activate** the scenario.

## End-to-end test

1. Run a watcher scenario manually (▶ **Run once**) — confirm Module 3's
   parsed JSON looks right and, if `relevant: true`, that a record appears in
   the `Job Alerts` data store (Data stores → `Job Alerts` → view records).
2. Run the digest sender manually — confirm you get a Telegram message and
   that the record(s) you just added flip to `notified: true` in the data
   store afterward.
3. Run the digest sender again immediately — confirm it sends nothing (the
   "Has new jobs" filter should skip it, since everything is now notified).
